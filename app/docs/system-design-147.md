# Remembra 1-4-7 System Design (Free-Tier)

## Goal
Implement a strict long-term retention flow with deterministic intervals:
- Stage 0 (new): review at `cycle_started_at + 1 day`
- Stage 1: review at `cycle_started_at + 4 days`
- Stage 2: review at `cycle_started_at + 7 days`
- Stage 3: decision state after day-7 (`Add Day 30` or `Complete`)
- Stage 4 (optional): review at `cycle_started_at + 30 days`
- Completion queue: auto-delete `20 days` after completion

Pass/fail rule:
- Pass (`good` or `easy`): advance one stage
- Fail (`again` or `hard`): reset to Stage 0 and set `cycle_started_at = today`

## Architecture
- Frontend: React + Zustand (`app/src/store`)
- Domain layer: pure scheduling math (`app/src/domain/review147.ts`)
- Service layer: data/auth/ai/notifications (`app/src/services`)
- Backend: Supabase Postgres/Auth/Storage/RLS (`app/supabase/schema.sql`)
- Android shell: Capacitor (`app/android`)

## Data Model
Primary table: `memory_items`
- Scheduling fields:
  - `cycle_started_at` (DATE)
  - `review_stage` (0..4)
  - `next_review_date` (DATE, null while awaiting 7th-day choice or completed)
- Compatibility fields kept for current app contracts:
  - `current_stage_index`, `review_template`, `interval`, `repetition`, `easiness_factor`
- Lifecycle fields:
  - `completed_at`, `mastered_at`, `archive_at`, `delete_at`

Supporting tables:
- `profiles`, `categories`, `reviews`, `streak_entries`, `achievements`, `device_push_tokens`

## Scheduling Invariants
- Trigger `enforce_memory_item_147_trigger` enforces 1-4-7 state consistency on insert/update.
- Trigger also supports optional day-30 reinforcement stage.
- Any legacy status values are normalized:
  - `learning/reviewing -> active`
  - `mastered -> completed`
- Completed rows enforce:
  - `next_review_date = null`
  - `delete_at = completed_at::date + 20`

## Review Flow
1. Read memory item.
2. Compute transition with `process147Review(...)`.
3. Persist updated item.
4. Append event to `reviews`.
5. After day-7 completion, app asks user:
   - add day-30 reinforcement
   - complete topic
6. Completed topics remain in completed queue and auto-delete after 20 days.

## Notification Flow
- Local reminders:
  - Per-item review notification at next due date/time
  - Daily summary notification
- Message text generated by AI service (`generateReviewReminderMessage`, `generateDailyReminderSummary`)
- Push token registration:
  - Captured via Capacitor Push Notifications
  - Persisted in `device_push_tokens` for future remote push dispatch

## Image Storage Flow
1. Upload image to Supabase Storage bucket `memory-images`.
2. Store attachment metadata (`url`, `path`, `bucket`, `mime_type`) in item.
3. On item delete, remove corresponding storage objects.

## Free-Tier Strategy
- Single Supabase project:
  - Postgres + Auth + Storage + RLS
- Use local notifications by default to avoid paid push infra.
- Optional free AI providers:
  - Groq primary
  - OpenRouter fallback
- No always-on paid servers required.

## Deployment Runbook
1. Run full SQL once in Supabase SQL Editor:
   - `app/supabase/schema.sql`
2. Set env vars:
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_ANON_KEY` or `VITE_SUPABASE_PUBLISHABLE_KEY`
   - `VITE_GROQ_API_KEY` (optional)
   - `VITE_OPENROUTER_API_KEY` (optional fallback)
3. Build and sync Android:
   - `npm run android:sync`
4. Open Android project:
   - `npm run android:open`
5. For remote push delivery (optional), add FCM project config and service credentials.

## Validation Checklist
- Auth:
  - Email sign-up/sign-in, password recovery, session restore
- Retention:
  - New item due in 1 day
  - Pass progression: 1 -> 4 -> 7 -> (choose day-30 or complete)
  - Optional reinforcement progression: 1 -> 4 -> 7 -> 30 -> complete
  - Fail resets to Stage 0 and restarts cycle
- Storage:
  - Image upload URL saved and displayed
  - Deleting item removes storage objects
- Notifications:
  - Next review and daily summary scheduled
  - Completed/deleted items have reminders cancelled
